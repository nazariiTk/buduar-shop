# Правила розробки проєкту «Будуар» (Antigravity Rules)

Детальна специфікація магазину, ролей, маршрутів та дизайн-системи описана у файлі `@[SPEC.md](./SPEC.md)`.

## 1. Технологічний стек і структура папок
* **Фронтенд:** React 19, Vite 8, React Router v7, Tailwind CSS v4 (`@tailwindcss/vite`), Zustand v5, Lucide React.
* **Бекенд і БД:** Supabase (PostgreSQL, Auth, Storage, Edge Functions на Deno/TypeScript).
* **Структура проєкту:**
  * `src/components/` — перевикористовувані UI-компоненти вітрини та `src/components/admin/` для адмінки.
  * `src/pages/` — сторінки публічної вітрини та `src/pages/admin/` для адміністративної панелі.
  * `src/store/` — глобальні стори Zustand (`useCartStore.js`, `useAiMetricsStore.js`).
  * `src/services/` та `src/lib/` — клієнт Supabase (`supabase.js`) і сервіси роботи зі сховищем.
  * `supabase/migrations/` — усі SQL-міграції схеми БД та RLS-політик.
  * `supabase/functions/` — серверні Edge Functions (`create-order`, `nova-poshta`, `parse-product`, `sitemap`).

## 2. Архітектурні принципи та якість коду
1. **Малі та чисті компоненти:** уникати монолітних файлів; виносити повторювану розмітку та бізнес-логіку в окремі підкомпоненти, хуки або утиліти без дублювання коду (DRY).
2. **Сувора типізація та чистота:** не використовувати `any` у TypeScript-файлах (Edge Functions / нових модулях), не залишати невикористаних змінних чи імпортів.
3. **Заборона хардкоду кольорів і шрифтів:** усі кольори, шрифти та відступи у клієнтській частині мають братися виключно з дизайн-токенів (CSS-змінних / теми у `src/index.css`). Палітра стилю «Французький будуар»: слонова кістка `#F6F0E6`, запилена троянда `#D9B8B0`, бордо `#6B1F2A`, антична позолота `#B8975A`, глибокий графіт `#2B2625`.
4. **Заборона нових залежностей без дозволу:** категорично заборонено встановлювати нові npm-бібліотеки без попереднього запитання та згоди користувача.
5. **Обов’язкова автоперевірка після кожної задачі:**
   * Після будь-яких змін у коді агент **зобов’язаний** запустити перевірку (`npm run lint` та `npm run build`, а при наявності `typecheck`/`test` — єдиний скрипт перевірки) і виправити всі помилки до завершення відповіді.
   * Для візуальних змін у UI агент має перевіряти результат у браузері та робити скріншот.

## 3. Безпека Supabase та цілісність даних
1. **Row Level Security (RLS):**
   * Усі таблиці в схемі `public` повинні мати увімкнений RLS (`ENABLE ROW LEVEL SECURITY`).
   * Усі представлення (`VIEW`) повинні мати `security_invoker = true` (`ALTER VIEW ... SET (security_invoker = true)`).
   * Роль `authenticated` — це звичайний зареєстрований покупець. Права на зміну каталогу (`products`, `product_skus`, `product_photos`, довідники) та перегляд усіх замовлень/клієнтів дозволені **виключно** адміністраторам через функцію `public.is_sync_admin()`.
2. **Ключі та секрети:**
   * У фронтенді дозволено використовувати лише публічний `VITE_SUPABASE_ANON_KEY`. Ключ `service_role` та приватні секрети живуть виключно в змінних середовища Supabase Edge Functions або бекенд-скриптів, а `.env` завжди залишається в `.gitignore`.
3. **Серверна валідація фінансів:**
   * Ціни, знижки, наявність товару на складі та підсумкова сума замовлення рахуються і перевіряються **тільки на сервері** (в Edge Functions або SQL RPC), ніколи не довіряючи числам із браузера.
   * Статус оплати замовлення змінюється тільки через верифікований серверний webhook платіжної системи.
4. **Міграції та правила каталогу:**
   * Будь-які зміни схеми БД або політик RLS оформлюються як SQL-міграції у `supabase/migrations/`.
   * **КАТЕГОРИЧНО ЗАБОРОНЕНО** автоматично створювати нові значення в довідниках (`brands`, `colors`, `sizes`, `materials`) під час AI-парсингу товарів — лише ручне створення оператором через кнопку `+ Ств.`.
   * У таблицях довідників та товарів використовується поле `name` (не `name_uk`). Слово «група» («групи товарів») не вживається в інтерфейсі та новому коді — використовуємо «Товар» / «Картка товару».

## 4. Процес роботи
* Перед реалізацією нетривіальної задачі спершу скласти короткий план і узгодити його з користувачем.
* Виконувати роботу малими атомарними кроками (одна фіча або виправлення за раз).
* Якщо під час виправлення помилки дві-три спроби поспіль не дають результату — зупинитися, проаналізувати першопричину разом із користувачем або запропонувати відкат до чистого стану замість хаотичних правок.
